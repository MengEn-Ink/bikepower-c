# 鬥骑序列号修复与刷写验证

## 结论与范围

用户授权补齐序列号并刷写最新固件，目标为本次华为P50E/鬥骑2.6.6复现所用的generic-c3开发板。已完成代码、专项回归、当前源码ESP-IDF 5.5.4独立构建、串口刷写和回读验证，保留原骑行与桥接配置。

默认序列号从空值改为15字节的 `BP-` + 出厂eFuse标识的12位大写十六进制；在BLE host启动前初始化、静态缓存，重启不变。已有非空DIS覆盖值优先，清空覆盖时回退默认值。不新增NVS键，不改运动协议UUID、通知内容或本次用户参数。

用户已反馈“可以了”，确认此前失败的鬥骑功率计入口在刷写后可用，并授权提交代码及发布新版本。该反馈是人工复测结果，不等同于自动化一分钟数据连续性或长时App验收。根因具体App代码分支仍未取得；该轮同时更新至最新已提交BLE能力，包含真实桥接CPS/CSC-only布局，因此不能将成功全部视为严格单变量序列号A/B结论。

## 失败证据与候选原因

USB主复现中手机成功建链、成功发现CPS及2A63/2A65/2A5D，厂商、型号、固件读取成功；序列号2A25读取回调Status=0后，鬥骑没有继续处理该字段、读取硬件/软件版本或订阅功率。独立电脑读取2A25成功但0字节，随后可接收功率。

最强候选是鬥骑设备信息初始化对空值的处理；没有App源码，不能断言具体代码分支。早前旧链路重用另有reason=0x08超时/status=133，保留为次要异常，不用它解释后续持续连接中的初始化停滞。

原始诊断见 `tests/reports/qidou-usb-diagnosis/`，本轮验证见 `tests/reports/qidou-serial-fix/`。

## 真机差异与测试修正

当前配置已选择真实来源，八组读取确认未改；最新已提交代码在该配置下只注册/广播CPS/CSC，而旧板上镜像仍含FTMS。因此初次刷写后测试脚本要求2ACC存在失败；保留 `after-initial-ftms-expectation.json`，后按配置实际能力分支验证，未为了通过测试修改设备来源或开启FTMS。

NVS回读窗口覆盖0x9000至0xFFFF：PHY区字节不变，NVS最后一页0xE000变化，因此**不是NVS介质逐字节完全不变**。有效八组配置与身份覆盖前后、重启后均一致；整片原Flash备份保留。变化可能与最新存储初始化/迁移或运行时提示写入有关，本轮未进一步拆解页内键值，不能宣称已证明具体写入键。

默认系统环境指向不存在的IDF工具目录；通用export要求未安装的Xtensa/ULP工具。最终只在命令进程设置IDF路径和C3工具链PATH，使用项目build/toolchain中已存在的5.5.4框架，不修改持久系统变量。Windows无host编译器，使用同一源码快照在Linux回归。新测试首次替身声明/宏缺失已修正后完整复跑，不改变生产逻辑或放宽断言。

## 用户复测

设备已上电、电脑蓝牙连接已释放。打开鬥骑，使用原功率计入口重新搜索BikePower；如App保留旧绑定，可在App内移除该设备再搜索，不必清全部App数据。
