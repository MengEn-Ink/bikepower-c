# Service Changed 重启恢复设计与验证

## 问题与方案

布局变化后，`ble_bond_cache_sync` 持久保存新摘要，并保留 Service Changed
CCCD 的 `value_changed`。`on_sync` 仅在摘要变化时调用系统
`ble_svc_gatt_changed`。设备在对端确认前再次启动时，摘要相同，而系统服务
的起止句柄是未持久化的静态变量，默认零；绑定恢复可能编码出无效的 `0–0`。

采用缓存模块在成功同步后检查待确认 Service Changed 的方案。存在合法
indication 订阅且 `value_changed=1` 时，调用系统入口恢复 `1–65535` 范围；
没有待确认记录则不通知。所有读取失败阻断广播，不清密钥或用户配置。
系统入口会标记所有已订阅 peer；若只有部分 peer 待确认，其他已确认 peer
可能重复收到一次完整范围指示，仍采用协议栈原有队列与确认生命周期。
`changed` 仍只表示布局摘要是否变化，不扩展其语义。

系统范围更新入口返回 void；其内部持久化失败会被项目安全存储回调锁存。
`on_sync` 在缓存同步返回成功后仍检查该锁存状态，失败则阻止首次广播，
避免把未完成的存储操作当作正常启动。

另一方案是每次启动无条件通知，代码较少但会重复标记已确认客户端，造成
不必要的重新发现。新增持久范围字段则增加 NVS 状态与迁移成本；现有完整
范围常量足以覆盖删除的旧句柄，无需新增 schema。

影响仅为系统 GATT 缓存失效恢复；运动通知、FTMS、配置事务与广播服务组合
保持原有约束。Windows 的实际 ACL 占用仍需实物证据，不能据此宣称解决。
