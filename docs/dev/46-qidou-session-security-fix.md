# 鬥骑会话加密修复与手机验收

## 结论（2026-11-07）

用户确认“鬥骑软件现在能够正常连接了”。同一修复候选的手机 USB 日志确认：Secure Connections Just Works 配对成功，链路加密开启，FTMS Request Control 和 Start/Resume 成功，原“配对失败—手机拆链—应用重连”循环在本次采集窗口消失。该结论限于本次连接场景，不等于所有客户端、所有控制操作或完整发行门禁均通过。

## 根因与最小变更

当前 ESP-IDF 5.5.4 所带 NimBLE 编译期绑定分支默认启用，但项目运行时 `sm_bonding=0`、最大绑定数为0，且没有安全存储读取回调。配对前置容量检查可能将缺存储返回的 ENOTSUP 作为错误；重复配对检查只把 ENOENT 视为没有旧绑定。手机原始 Unspecified Reason 单独不能唯一定位到哪一行，但当前源码分支回归与修复后安全协商成功互相印证。

- 顶层 CMake 只给本项目 bt 组件定义 `MYNEWT_VAL_BLE_SM_BONDING=0`，不修改第三方 IDF。
- `session_security_store_read` 对本项目支持的持久对象返回 ENOENT，对空 key/value 返回 EINVAL，对未知对象返回 ENOTSUP；不写出虚构密钥，不进行持久化。
- NimBLE 初始化成功后、host 线程启动前接入 `configure_session_security`，保留 SC、无IO、无MITM、无bond。
- 骑行/跑步 FTMS Write Encryption、UUID、通知格式、默认序列号和用户配置不变。
- `test_ble_session_security.py` 抽取真实生产函数验证参数/对象/输出未改写及初始化时序。指定 `--idf-host-src` 时再抽取当前 IDF 的存储/容量/重复配对前置函数：当前分支通过，缺回调导致ENOTSUP，恢复编译绑定容量分支也复现ENOTSUP。计数调用仍为受控故障替身，不声称完整旧版SMP协议栈模拟。
- 专项接入质量、quick/full 和双板构建前门禁。

## 已刷候选与保持性

现场为 generic-c3，固件版本4.3.2、构建Git元数据669127d，源码dirty；不是原v4.3.2发行镜像。应用1,138,672字节，SHA256为 `d501cc24bce365b2d392196fe82838e432a2982ad29feb1eeb9b35bf469e663f`。只写0x10000应用区；完整Flash回读应用逐字节一致。当前源码的安全变更与已刷候选一致，后续仅测试/门禁/文档改变，不重新刷写、不干扰用户正在使用的手机连接。

当前4MiB完整Flash和八组/DIS覆盖私有备份留本机。刷后配置、身份和默认序列号摘要保持；电脑成功控制后再次完整八组回读一致。完整NVS字节比较的失败保留，经真实IDF记录解析确认差异只在 `phy/cal_data` 射频校准记录，用户namespace记录与CRC保持；不声称所有NVS字节不变，也未捕获写校准记录的运行时调用栈。

## 回归与未闭合边界

- IDF候选构建0错误，125个bt编译单元携带无绑定定义。
- Host6237/0、生产BLE标准/序列号/骑行能力、门户保存、相关静态通过；保留已有host `strnlen` 编译警告。
- 核心mock耐久15轮/180.5秒通过，不替代真实无线/实体按钮。
- Windows首次未加密ATT0x05、正常配对后Request/Start/非法功率/320W/Stop响应均正确；四路各12帧、最后324W，堆155460字节，state1/profile0，配置一致。
- Windows后续第一次GATT发现Unreachable，完整配置E2E未取得快照、未开始写入即失败，独立末次回读也失败；双次重连未运行。未删除Windows配对记录来绕过，原因尚未确认。
- 跑步加密控制、m5stamp实物、实体按钮/LED、长时无线/完整跨App门禁不在本次手机连接验收内；历史结果不移植到本候选。
- 本次仅提交修复和相关测试记录，版本不升、不建新tag/Release、不覆盖已发布附件。

本机证据目录：`tests/reports/qidou-security-fix/`。分发只用聚焦脱敏摘要/摘录，完整Flash、全组wire、全缓冲日志和设备身份不公开。首次采集文件的输出曾延迟到收尾，结论来自实际文件与后续只读缓冲/状态，不由ready标记或空文件推断。
