### 目前的实测结论

- 原15秒data_timeout：开发板曾将实际活跃GATT链路当作未连接，丢弃码表订阅并拦截通知。最小修复后目标踏频首段101秒、功率对照107秒和原混合配置下已保存功率重连122秒均未出现该超时；第二次踏频只17秒，不能宣称两次60秒或长期耐久全部通过。
- 功率首次搜索：原混合服务首次分类偏向CSC/cad；临时移除CSC/HRS后能发现并保存功率，保存后恢复混合服务仍能pwr重连。支持首次分类/角色登记兼容问题，不是BINAVI完全不支持BLE功率，也不是混合模式完全不能传功率。对照保留FTMS，并非严格CPS-only。
- 三路使用：电脑同一连接CPS17/CSC17/HRS16条正常，码表只订阅所选角色的表现与单下游连接后停止广播应分开；未验证BINAVI自动在同一设备接收三角色。心率单独目标验收仍未做。
- 踏频列表：cbsc转cad后成功收数，未见新增cad保存事件，角色保存/展示为候选问题，未定位确切客户端保存bug。不能制造假轮速解决列表。
- 详情字段：实际页面有传感器ID、制造商、软件版本、型号、序列号，没有名称字段。BikePower标准DIS非空，码表实际读取制造商/序列号/固件/软件并服务端rc0，型号未观察到读回调，页面仍`--`；HR40也有软件V1.01且曾进入码表记录，连接正常84秒时页面仍`--`。更支持码表详情映射/保存/显示限制，具体环节未证实。HR40型号/序列号不存在，不能替代CPS同类别对照；制造商能显示的原因尚未知。

### 后续优化项：需要先有证据，当前不实施

- **发现兼容优化**：若继续开发，优先把“对外首选角色/广播呈现”和“实际提供的数据服务”分开评估，形成显式可选的码表兼容方案，而不是永久删CSC/HRS或让配置掩码长期停在1。应分别验证未保存的新搜索、已保存重连、HRS发现、同地址多角色及原客户端回归。可能涉及`main/ble_bikepower.c`广播组装；若新增可持久配置，还需领域配置/编解码/NVS/门户及相应契约同步。这是后续设计方向，不是本轮已验证修复，当前不指定唯一广告顺序或承诺三路同时解决。
