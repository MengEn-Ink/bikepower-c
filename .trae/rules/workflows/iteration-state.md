# 迭代推进模式（BikePower C）

<!-- stability: tier-2 (稳定，随协作方式调整) -->
<!-- rule-id-prefix: IT -->

> 每个新功能、缺陷修复或流程改动，都按“分析 → 预估 → 执行 → 验证”四步走，避免直接进入编码。

## 四步流程

### `IT-1`：分析

- 明确影响模块、状态机、内存、RF 互斥和测试面
- 先读 `project-context.md` 与相关 rules
- 编辑前运行 `git status --short`
- 如果会碰到用户未提交的相关文件，先判断是否冲突

### `IT-2`：预估

- 说明复杂度、风险、是否涉及真机验证
- 判断是文档改动、领域层改动，还是设备行为改动
- 明确需要更新哪些代码、规则、文档、脚本

### `IT-3`：执行

- 只修改当前任务必要文件
- 常量集中在 `bikepower_config.h` 或 `domain_config.h`
- 中断、BLE 回调、WiFi 射频切换严格遵守硬约束

### `IT-4`：验证

- 根据 `test-coverage.md` 选择最低合格测试集
- 设备行为改动按 `device-testing.md` 执行
- 把结果写入 `CHANGELOG.md` 或提交说明

## 退出条件

- `IT-5`：分析不清时，先补上下文，不得凭猜测落代码
- `IT-6`：验证未完成时，不得把任务描述成“已完全完成”
- `IT-7`：如果发现与既有规则冲突，先更新规则或向用户澄清，再继续实现
